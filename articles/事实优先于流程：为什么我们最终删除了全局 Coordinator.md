# 事实优先于流程：为什么我们最终删除了全局 Coordinator

## 摘要

在一个多仓、多票、多 Agent 协作的工程流程里，我们曾引入全局 Coordinator：统一解释当前阶段、任务所有权、Review 轮次、Monitor 状态、接管资格和发布许可。它在早期解决了真实的失控问题，却也随着体系演进逐渐成为第二套状态机——Git、票据、CI、部署平台记录一套事实，Coordinator 又维护一套“流程事实”。

问题在提测后的 UX 局部修复阶段集中暴露：本来只需修改一个局部交互、做定向验证和人工验收，却仍被迫重新经历票面同步、固定 Review、拼缝判断、Monitor 重挂、阶段推进和交接仪式。流程没有继续降低风险，反而开始制造等待、重复记账和恢复成本。

这次重构最终形成的核心判断是：

> **事实决定系统现在是什么；不变量决定下一步能不能做；流程只负责帮助人和 Agent 理解这两件事。**

删除全局 Coordinator 并不等于取消协调。我们删除的是覆盖整个 Feature 生命周期的抽象流程所有权，保留并强化的是与真实资源、候选身份和远端副作用直接对应的约束：worktree 写互斥、Frozen Manifest、发布 DAG、证据依赖、ActionKey、授权边界和运行验收。

最终决策可以压缩成一句话：

> **取消全局 Coordinator 和长期 Owner。调查、分析、Review、测试和不同 worktree 开发允许并发；同一物理 worktree 仅保留瞬时写互斥；远端副作用不建立执行者所有权，而以 Frozen Manifest scoped ActionKey 与平台事实实现去重、幂等和可判定重试。**

本文记录这次决策的背景、失败过程、两套设计哲学及各自的适用边界。

---

## 案例现场：一次局部修复为什么拖动了全局流程

问题集中暴露在一次复杂多仓功能完成首次提测之后。首次交付阶段需要协调多个仓库、Review、制品、消费者、部署顺序和运行验收，全局 Coordinator 在这个阶段确实提供了价值。

随着 Git、Ledger、CI、部署和运行事实逐渐完善，Coordinator 的角色却没有同步收缩：它仍然维护阶段、Owner、Review 轮次、Monitor 和接管状态，开始复制外部系统已经能够表达的事实。

```text
首次多仓交付
    │
    ▼
引入 Global Coordinator
统一阶段、Owner、Review、Monitor
    │
    ▼
早期有效：补足工程事实能力不足
    │
    ▼
Git / Ledger / CI / 部署事实逐渐完善
    │
    ▼
Coordinator 没有退出，开始复制已有事实
```

真正触发反思的是提测后的局部 UX 修复。这个修改本身只需要定向验证和局部发布，却仍然拖动了覆盖整个 Feature 生命周期的流程。

```text
一次局部 UX 修复
        │
        ├── 实际需要
        │     修改 → 定向测试 → 人工验收 → 更新候选 → 局部发布
        │
        └── 全局流程要求
              票面同步 → Review 轮次 → 拼缝判断
              → Monitor → 阶段推进 → 重新交接
                              │
                              ▼
                   流程成本超过风险收益
```

这次案例的主问题并不是“流程步骤太多”，而是：

> **全局 Coordinator 同时承担进度记录、执行许可和中断恢复，逐渐成为独立于 Git、CI 和部署平台之外的第二事实源。**

等待、重复记账、无冲突任务被串行化以及恢复成本上升，都是这个问题的结果。

## 背景：一个原本合理的全局控制面

场景并不简单。一个完整 Feature 可能同时包含：

- 多个 Git 仓库；
- 多张需求票和缺陷票；
- 多个并行实施 Agent；
- 独立 Review 与跨票组合 Review；
- DDL、公共 API、服务端、消费者和前端；
- CI、制品发布、部署和运行验收；
- Agent 中断后的接管与恢复。

早期最大的风险是“没人知道整体做到哪里”。

一张票可能已经实现，却没有固定提交；一个仓库可能通过 Review，消费者却没有重建；CI 可能是绿的，新 Pod 却没有接流；Agent 可能中断，后续参与者无法判断哪些步骤已经发生。

于是我们引入了一个全局 Coordinator：

```text
                    Feature
                       │
                Global Coordinator
                       │
       ┌───────────────┼────────────────┐
       ▼               ▼                ▼
 Implementation      Review          Delivery
       │               │                │
       ▼               ▼                ▼
   Agent / Ticket    Reviewer          Monitor
```

Coordinator 持有“全局工作流解释权”：

```text
现在在哪个阶段？
哪张票完成了？
谁是当前 owner？
谁能继续执行？
Review 是否结束？
是否允许进入拼缝？
是否允许发布？
Agent 挂了谁 takeover？
Monitor 是否还活着？
```

它背后的哲学是：

> **只要把执行过程组织得足够严格，就能够保证最终结果正确。**

换成公式就是：

```text
正确执行
≈
正确地走过 Workflow
```

这并不是一个愚蠢的设计。恰恰相反，在工程事实尚不完整时，它是非常自然的补偿性控制面。

当系统还没有稳定的交付语义账本、Frozen Manifest、发布 DAG、证据依赖模型和平台事实回读时，Coordinator 实际上替系统记住了：

```text
我们做到哪了
谁做过什么
接下来应该谁做
哪些东西验证过
哪些动作还没执行
```

旧 Coordinator 解决过真实问题。问题在于，随着事实基础成熟，它逐渐承担了超过必要范围的责任。

## 问题定义：Coordinator 成为第二事实源

局部 UX 修复只是触发器，真正的问题是全局流程状态开始与工程事实竞争解释权。

复杂首次交付通常确实需要：精确候选、独立 Review、组合关系检查、发布顺序、制品依赖、消费者重建和运行验收。此时较强的流程成本与爆炸半径基本匹配。

但进入提测后的局部修复阶段，同样的全局流程不再提供与成本相称的风险收益。原本用于控制首次复杂交付风险的机制，开始无差别地作用于低风险局部变化。

更严重的是，多份状态开始描述同一件事：

- 票据记录“做到哪里”；
- Git 记录代码事实；
- audit 文档记录阶段和结论；
- deploy checklist 记录发布对象；
- Coordinator 记录 owner、phase 和 ready；
- Monitor 记录任务是否仍在运行；
- CI 和部署平台记录远端状态。

任何一处没有同步，系统就需要额外 reconcile。所谓“为了可恢复而记录更多状态”，反而让恢复变成了对多份状态的考古。

最典型的错误是：

```text
流程说：Review 已完成
事实说：候选 SHA 已变化

流程说：Delivery READY
事实说：consumer 没有重建

流程说：部署成功
事实说：新 Pod 没有接流

流程说：Monitor 存活
事实说：观察的是旧 operation
```

此时系统最危险的不是“流程很多”，而是：

> **流程状态开始拥有推翻工程事实的权力。**

---

## 第一次收敛并没有解决根因

面对流程变重，第一反应通常不是删除 Coordinator，而是继续优化 Coordinator。

这些优化都有局部价值，却没有解决核心问题：

| 尝试 | 解决了什么 | 为什么没有解决根因 |
|---|---|---|
| 缩小 Handoff Contract | 降低交接文本和上下文成本 | 仍然依赖流程状态恢复现场 |
| Monitor 输出降噪 | 减少无效通知 | 仍然需要维护 Monitor 生命周期和所有权 |
| 收敛 takeover 字段 | 简化接管记录 | 仍然把恢复建模成接管旧流程 |
| 划清 Review 与拼缝职责 | 减少职责重叠 | 固定阶段仍然作用于所有变化 |
| 为 UX 快修改低验证档位 | 降低部分验证成本 | 仍然需要经过全局阶段推进 |
| 减少重复文档 | 降低部分记账成本 | Coordinator 仍然是一套独立状态源 |

它们优化了流程的局部成本，却没有改变以下事实：

```text
工程事实之外
仍然存在一套独立的工作流状态
```

只要全局 Coordinator 仍需要维护：

```text
Owner
Phase
Round
Terminal
Monitor
READY
Takeover
```

系统就仍然需要回答：流程状态和工程事实冲突时，到底相信谁？

如果答案不是“无条件相信工程事实”，所谓 SSOT 就并不成立。

这促使我们把问题从“怎样优化 Coordinator”改写为：

> **系统的正确性究竟由什么证明？**

## 新哲学：事实优先于流程

新模型最核心的变化是：

```text
旧模型                         新模型

Workflow State                 Engineering Facts
      │                               │
      ▼                               ▼
解释工程现场                    投影工程现场
      │                               │
      ▼                               ▼
Owner 决定谁能做                不变量决定能否做
      │                               │
      ▼                               ▼
恢复旧流程身份                  重新读取当前事实
```

以前 Agent 中断，我们试图恢复：

```text
Coordinator = A
Phase = Review
Review Round = 3
Monitor = M12
Status = READY
```

这些都是关于工作过程的描述。

真正决定工程现场的则是：

```text
repo A = commit abc123
repo B = commit def456

artifact X = 1.3.7

Frozen Manifest = sha256:xxx

deploy operation = 987
status = running

runtime AC = unverified
```

只要这些事实可以稳定读取，任何新的 Agent 都可以重新回答：

```text
当前交付对象是什么？
哪些提交属于候选？
哪些依赖尚未完成？
哪些动作已经在远端发生？
哪些验证仍然缺失？
下一步允许做什么？
```

于是 Agent 中断后的恢复模型变成：

```text
Ledger
+ Git
+ Frozen Manifest
+ Artifact / CI / Deployment / Runtime Facts
        ↓
重新投影当前工程现场
```

恢复的是工程事实，不是旧 Agent 的步骤、终端、Monitor 或 workflow phase。

流程仍然可以存在，但它只能是派生视图：

```text
流程可以导航
流程可以解释
流程可以展示

但流程不能证明事实
流程不能替代事实
流程不能覆盖事实
```

## 删除全局 Coordinator，不等于删除协调

这里最容易产生的误读是：

```text
删除 Global Coordinator
＝ Agent 可以随意并发
＝ 系统不再需要所有权、顺序和门禁
```

这不是新设计。

新设计删除的是**覆盖整个 Feature 生命周期的抽象流程所有权**，不是删除真实世界中的冲突和约束。

### 同一 worktree 的写冲突仍然存在

如果两个 Agent 同时修改同一个物理 worktree，可能产生：

- Git index 冲突；
- 生成文件互相覆盖；
- lockfile 漂移；
- 格式化或清理命令影响另一方；
- 提交边界被破坏。

这个约束必须保留，但它不需要一个 Feature 级 Coordinator。更准确的表达是：

```text
worktree-scoped transient mutex

锁的是：物理 worktree
保护的是：真实写冲突
生命周期：写操作开始到结束

不锁：Feature
不锁：整个 repo
不锁：Agent 身份
不保存：workflow phase
```

读、搜索、影响分析和 Diff 可以并行；只有真实写操作需要短生命周期互斥。不同 worktree 仍然可以并行修改。

### 远端发布仍然需要约束

真正需要保证的不是：

> 某个 Agent 永远拥有这条发布链。

而是：

> 对同一个冻结候选中的同一个远端动作，不能产生两个无法区分的副作用。

因此我们不再设计 `ExecutorOwner + Lease + Heartbeat + Takeover`，而是定义稳定的动作身份：

```text
ActionKey
= FrozenManifestDigest
+ Environment
+ ActionType
+ Target
```

副作用闸验证：

- Frozen Manifest 是否仍然匹配；
- 动作是否属于该候选；
- 发布 DAG 前驱是否完成；
- 环境和目标是否正确；
- 用户授权是否覆盖当前候选与动作；
- 平台是否已经执行过同一个 ActionKey。

新哲学不是“无协调”，而是：

> **协调必须绑定真实资源、真实动作和真实副作用；不能绑定抽象流程身份。**

## 删除 Coordinator 的哲学：正确性来自不变量，而不是所有权

全局 Coordinator 模型倾向于这样表达安全：

```text
只有 Coordinator 可以推进
只有当前 Owner 可以执行
只有进入某个 Phase 才能做下一步
只有 Monitor 仍在线才认为流程可继续
```

删除之后，问题被重新表述为：

```text
这个 worktree 现在是否有人写？
这个 commit 是否属于当前候选？
这个证据依赖的对象是否发生变化？
这个远端动作的前驱是否完成？
这个 ActionKey 是否已经产生副作用？
平台当前事实是否仍与授权时一致？
```

这些问题不依赖“当前 Coordinator 是谁”，而依赖一组可以检查的不变量：

- 资源互斥不变量；
- 候选身份不变量；
- 证据依赖不变量；
- 发布前驱不变量；
- 远端副作用幂等不变量；
- 授权范围不变量。

这更接近分布式系统的基本思想：

```text
不要依赖“某个进程记得自己正在做什么”

而要依赖：
任何参与者都能读取事实
任何动作都能验证前置条件
任何重试都能识别既有副作用
任何中断都能重新投影现场
```

删除全局 Coordinator 的收益也不只是“少一个 Agent”：

- 并行分析不再被 Feature 所有权串行化；
- Agent 退出不再造成流程身份悬挂；
- Monitor 不再为了维持“活着”而产生噪音；
- 历史步骤不再冒充当前事实；
- 恢复从“接管旧流程”变成“读取当前现场”；
- 治理规则不再侵入每一次普通执行。

## 不删除 Coordinator 的哲学：用单一解释者对抗事实缺失

但“不删除”并不等于落后。

在另一类系统里，全局 Coordinator 仍然是正确设计。它背后的哲学是：

> **当系统无法仅凭外部事实可靠恢复意图、顺序和责任时，需要一个单一解释者维持长事务的一致性。**

典型情况包括：

- 外部平台没有稳定查询接口，动作发生后无法 reconcile；
- 远端动作没有幂等键，重复执行会造成不可逆损失；
- 跨系统长事务需要明确的补偿顺序；
- 业务要求任何时刻必须存在唯一责任人；
- 事实来源不完备，无法从 Git、平台和制品状态重建意图；
- 多个参与者操作同一不可分割资源，无法通过资源级锁隔离；
- 流程本身就是业务对象，例如审批、资金或合规签署。

在这些场景中，Coordinator 保存的并不只是“方便看的状态”，而是外部世界尚未提供的必要事实：

```text
Intent
Compensation Plan
Exclusive Ownership
Approval Chain
Irreversible Step Boundary
Unobservable External State
```

此时过早删除 Coordinator，表面上减少了控制面，实际上只是把状态转移到了：

```text
人的记忆
聊天记录
临时终端
群消息
未提交文件
“应该已经做过”的猜测
```

这不是事实优先，而是事实缺失。

所以保留 Coordinator 的合理边界是：

> **它保存的是无法从其他系统重建、但对安全推进又不可缺少的最小状态。**

一旦这些状态已经被 Git、Ledger、Manifest、平台操作记录、幂等键和运行事实表达，Coordinator 就不应继续复制一份。

## 两种哲学的适用边界

真正的判断标准不是团队喜不喜欢 Coordinator，也不是 Agent 数量多不多，而是：

> **如果 Coordinator 消失，系统还能否仅凭持久事实，安全、确定地回答“现在是什么状态、下一步能做什么、重复执行会不会出事”？**

如果答案是“能”，全局 Coordinator 大概率已经是重复状态。

如果答案是“不能”，还要继续追问：

```text
不能，是因为确实存在不可观察的长事务？

还是因为我们还没有把事实、幂等和资源边界建设好？
```

### 适合删除全局 Coordinator

- 工程对象有稳定 SSOT；
- 当前状态可以从 Git、Ledger 和平台事实重建；
- 并行任务大多彼此独立；
- 物理冲突可以下沉到资源级互斥；
- 远端动作有稳定身份、可查询、可去重；
- 证据是否有效可以由依赖关系判断；
- 流程阶段只是展示，不承载独立业务语义。

### 适合保留全局 Coordinator

- 长事务存在不可观察步骤；
- 补偿动作必须由单一主体按顺序执行；
- 外部副作用无法可靠查询或去重；
- 唯一责任人本身是业务或合规要求；
- 系统尚未建立足以恢复现场的事实基础；
- 操作对象无法拆成更小的资源边界。

### 常见的中间形态

删除 Feature 级全局 Coordinator，并不妨碍保留：

```text
worktree 写互斥
单次发布 Runbook
DDL migration controller
某个不可逆动作的局部 executor
短生命周期 observer
```

这些不是全局工作流所有者，而是**绑定特定资源或副作用的局部协调器**。它们在局部动作结束后即可消失，不拥有整个 Feature 的生命周期。

## 案例复盘给出的验收场景

这次决策不是只从抽象架构图推导出来的，而是结合复杂首次交付与提测后快速修复两类真实过程形成的。

复盘后可以看到，高价值保障集中在：

```text
精确交付对象
真实组合边
制品与消费者关系
发布顺序
运行是否生效
不可逆副作用
```

低价值成本则集中在：

```text
每票同强度复核
Markdown 多源记账
固定阶段推进
常驻接管仪式
Monitor 生命周期维护
用流程字段复制平台状态
```

基于这些过程，进一步整理出 8 类用于检验新模型是否发生工程倒退的验收场景：

| 场景 | 必须保留的能力 | 防止的工程倒退 |
|---|---|---|
| 首次多仓发布 | 精确候选、DDL/制品/消费者/前端时序、强证据 | 把复杂首次交付错误降级成 UX 快修 |
| 零代码重建 | 发布对象不等于源码改动仓 | Manifest 退化成 commit 列表 |
| branch-tip 夹带 | SHA 冻结、未绑定提交阻塞 | 用分支 tip 冒充候选 |
| UX 快修 | 定向验证、人工验收、局部发布 | 固定 E2E/复核重新回潮 |
| 组合拼缝 | 组合边、共同旅程、回退耦合 | 因删除固定阶段而漏掉组合风险 |
| 高风险单仓 | 风险按语义而非文件数判断 | “单仓/单文件等于低风险”误判 |
| 运行假绿 | CI、部署、运行事实分层 | pipeline 绿冒充上线和可用 |
| 中断恢复 | 本地 SSOT + Git 现场恢复 | 重建 takeover/terminal 状态机 |

这组场景非常重要。它确保我们删除的是流程冗余，而不是历史上真正防住事故的能力。

## 重构后的最小模型

### 1. 交付语义账本

Ledger 只记录 Git 和平台无法直接表达、但交付需要的领域事实，例如：

- 票与仓库的关联；
- 候选提交的选择、排除和替换；
- 依赖和发布顺序；
- 零代码消费者重建；
- 目标环境与授权范围；
- 风险、证据引用和未验证项；
- 远端动作引用与运行结论。

Ledger 是 append-only 的领域事实账本，不保存 `workflowPhase`、`owner`、`heartbeat` 或通用 `StatusChanged`。

### 2. Working Manifest 与 Frozen Manifest

Working Manifest 是从 Ledger、Git 和平台事实投影出的当前候选视图，可以持续变化。

Frozen Manifest 则在远端副作用前冻结：

```text
Tickets
Repos + Commits
Artifacts
Consumers
Deployment Targets
Dependency DAG
Rollback Boundary
```

它内容寻址、只读，不被 CI、部署和运行结果反向修改。后续结果继续追加到 Ledger。

### 3. 风险—证据模型

验证强度不再由固定阶段或票数决定，而由具体风险命题决定：

```text
首次复杂交付
→ 强证据、广域回归、组合验证

UX 局部修复
→ 定向验证、视觉/人工验收、受影响范围复核

高风险单仓修改
→ 即使只有一个文件，也按语义风险升级

存在跨票组合边
→ 才执行拼缝 Review
```

证据需要显式声明依赖。依赖发生变化，只让相关证据失效，不要求整个流程从头重跑。

### 4. 两个硬闸

重构后的控制模型重点保留两类跨阶段硬闸。

**候选冻结闸：**

- 精确 SHA 与制品；
- 无未解释夹带；
- 发布图闭合且无环；
- 目标和回退边界明确；
- 阻塞性缺口显式暴露。

**远端副作用闸：**

- 动作匹配 Frozen Manifest；
- 前驱已经完成；
- 授权仍然有效；
- 平台事实没有漂移；
- 重试不会制造重复副作用。

单 worktree 单写者是局部并发安全护栏，不发展成全局执行状态机。

## 迁移时为什么不能直接删除 Coordinator

如果系统今天仍依赖 Coordinator 保存必要事实，直接删除只会制造新的失控。

更稳妥的迁移顺序是：

```text
1. 盘点 Coordinator 当前保存了什么
        ↓
2. 区分工程事实、派生状态和临时执行状态
        ↓
3. 为工程事实建立唯一 SSOT
        ↓
4. 把物理冲突下沉到资源级护栏
        ↓
5. 为远端副作用建立 ActionKey、查询与去重
        ↓
6. 证明中断后可以从事实重建现场
        ↓
7. 删除全局 Owner、Phase、Heartbeat 和 Takeover
        ↓
8. 保留必要的局部协调器并明确生命周期
```

核心顺序是：

> **不是先删掉 Coordinator，再期待事实自己出现；而是先让事实足以承担正确性，再让 Coordinator 退出。**

## 可复用的架构检查表

以后遇到类似 Agent 控制面设计，可以先回答以下问题。

### 事实与状态

- 这个字段描述工程对象，还是描述执行过程？
- 它能否从 Git、制品、CI、部署或运行平台重新计算？
- 如果能重新计算，为什么还要持久化第二份？
- 当流程状态和平台事实冲突时，系统相信谁？

### 协调与并发

- 冲突对应哪个真实资源？
- 能否把 Feature 级锁缩小成 worktree、环境或动作级约束？
- 只读分析为什么需要被写操作串行化？
- 局部协调器能否在动作结束后消失？

### 远端副作用

- 动作是否有稳定 ActionKey？
- 平台是否可以查询已经发生的动作？
- 重试是否幂等？
- 用户授权绑定的是抽象流程，还是精确候选和动作？

### 恢复

- 新 Agent 能否在不读取旧会话的情况下恢复现场？
- 恢复依赖旧 owner、terminal、monitor 或 heartbeat 吗？
- 删除历史流程文件后，当前交付判断是否仍然成立？

### 流程价值

- 这个 Gate 具体防住了哪类真实事故？
- 它保护的是事实、不变量或不可逆副作用吗？
- 如果没有它，风险会增加，还是只是“看起来不完整”？
- 验证成本是否与爆炸半径匹配？

一个很实用的判断是：

> **如果一个 Gate 不能指出它保护的具体事实、不变量或不可逆副作用，它就不应该成为硬闸。**

## 最终结论

这次案例不是简单地证明“Coordinator 不好”。

旧模型和新模型分别建立在两套成立条件上。

旧模型认为：

```text
由唯一 Coordinator 维护正确流程
流程连续
所以系统可信
```

它适合事实能力不足、长事务不可观察、责任必须唯一的系统。

新模型认为：

```text
由持久事实描述工程现场
由资源边界隔离真实冲突
由副作用不变量约束不可逆动作
由按需投影产生流程视图

事实成立
所以系统可信
```

它适合工程事实成熟、动作可识别、现场可重建、并行可以按资源隔离的系统。

真正需要警惕的是两个极端：

```text
极端一：
因为害怕失控
把所有执行都收进一个全局状态机

极端二：
因为追求简单
在事实和幂等能力尚未建立时
提前删除所有协调
```

这次选择删除全局 Coordinator，不是因为流程没有价值，而是因为它所保存的大部分状态已经可以被更可靠的工程事实表达；它继续存在，反而制造重复真源、串行化和恢复成本。

> **该保留的不是 Coordinator 这个角色，而是它曾经保护过的真实不变量。**
>
> **该删除的不是所有流程，而是脱离事实之后仍试图支配事实的流程。**
